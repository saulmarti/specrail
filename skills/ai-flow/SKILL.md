# AI Flow
Do not require the user to mention AI Flow, a skill name, a task ID, or a CLI command. Use the global CLI internally and do not expose internal CLI instructions to the user. Two explicit prefixes override automatic routing: `Sin SpecRail:` / `No SpecRail:` means bypass SpecRail completely for that request (no SpecRail CLI, task, CodeGraph preflight, gate, evidence state, or learning); handle the remainder as an ordinary repository request. `SpecRail Fast:` explicitly authorizes the low-overhead governed mode below; create/intake that task with `--mode fast`. Never infer total bypass from ordinary wording.
## Deterministic control
1. Resolve existing work with `ai-flow resolve` by ID, exact title, or unique phrase. The task Markdown is the source of truth. When ambiguous, show the native task selector; never guess or create a duplicate. For explicit `Continue/Resume/Retoma TASK-####` requests, do not first search repository Kanban/memory/process files: resolve the task and read deterministic `next`/runtime state before manually loading any project workflow notes.
2. Show references as `TASK-#### — Title`, which are easy to reference in another chat by ID, title, or descriptive phrase.
3. Let SpecRail own CodeGraph lifecycle. Do not manually run `codegraph init`, `sync`, `status`, or `index` during a healthy task. SpecRail uses cached contract/health state and CodeGraph MCP watcher/catch-up; full reindex is an explicit Doctor repair only. Exception: active SpecRail Fast micro/light defers project-wide CodeGraph entirely unless the task escalates. On explicit Continue/Resume, read `next` first; when it returns `enter-phase-boundary`, enter and load the sealed capsule before any CodeGraph expansion or generic process reads.
4. Read `next`; its `readiness` field is the same deterministic contract used by `specrail readiness`, `why-blocked`, and Review Cockpit. Explain failed/stale gates and the returned shortest safe next action rather than inventing a status. If `specrail next` throws or exits non-zero, treat it as a runtime blocker: `readiness`/`why-blocked` remain diagnostics and never replace routing authority; do not mutate task/workflow or implementation state until `next` succeeds. Then explicitly load `.agents/skills/<recommendedSkill>/SKILL.md`. Do not rely on automatic mid-turn skill reselection and do not keep unrelated skills in context.
   - When `recommendedSkill` is `ai-flow-product-owner`, run the persistent project Product Owner. On `bootstrap-product-intelligence-context`, establish the concrete product/owner/audience project files before issuing any task verdict. On normal review, run it before the Product Specifier. In Guided, present every current Product Owner opinion (including `build`) for explicit acknowledgement; in Autonomous/Headless, a clean `build` may continue without interruption, while `revise` or `do-not-build` remains a human product decision, never an autonomous cancellation. Map the native choices deterministically: Continue → `product owner decide --decision proceed`; Review proposal → `--decision rework`; Reject task → `--decision reject`.
   - When `recommendedSkill` is `ai-flow-target-audience`, validate only profile IDs returned by `specrail audience profiles` through the public product surface after QA. Record the structured Target Audience review; do not substitute Builder or QA opinion. Map the native product choices deterministically: Accept trade-off → `audience decide --decision accept-tradeoff`; Review implementation → `--decision revise-implementation`; Review product → `--decision revisit-product`.
   - If `next.action` is `reapprove-hardened-specification`, show the supplied specification review and use native user input. Only after explicit approval call the normal specification-approval transition; never rebase or recreate the legacy Scope Guard baseline.
   - If `next.action` is `enter-phase-boundary`, the native boundary choice was already persisted in the prior turn. Do not show the selector again and do not read generic Kanban/memory/process files first. Immediately enter the boundary with the stable session, read `next` again, then load the sealed runtime handoff before any phase work.
   - At any post-approval execution/review point, treat bounded user feedback on the already-visible result as an incremental `REV-*` by default. A normal request for changes returning to Builder must use the revision path, keep the same task, and then follow the returned Revision Delta Capsule. Do not create a new task, regenerate planning, consume repair budget, or propose an Amendment merely because the user wants a small refinement. Use the broad/full return path only when the feedback changes governed product/specification/design/architecture/security/data/contract decisions or the incremental revision guard rejects it as material.
   - An explicit user instruction to **close/finish anyway** or **skip a named workflow step** is authoritative governance input, not another failed gate. Do not loop on the blocker or repeat that formal closure is impossible. For an explicit close/finish-anyway instruction, invoke the deterministic user-authorized close override once; it closes the task while recording that normal completion guarantees were waived. For an explicit skip instruction, record a user-authorized waiver for the named step only when the declarative workflow-gate registry marks it `waivable: true`, then continue from the resulting deterministic state. Never create an override autonomously or infer one from impatience; if the instruction is genuinely ambiguous, ask once. Once explicit, do not ask again and do not surface the same waived blocker through `next`/readiness.
5. Use one stable internal session token for the chat and pass it with `--session` to every `next`, `interaction`, `phase complete`, capability, and visualization command that can reach or describe a human gate. After `phase complete`, inspect the returned `next` immediately; when it contains an interaction, that returned interaction is the canonical gate payload. Obey `resolve-task-lease`; never let two chats write the same task concurrently.
6. Respect the approved specification hash, immutable QA mission hash, dependencies, repair budget, evidence gates, and `context.policy` progressive budget. Keep context small.
7. At a human gate, never construct or paraphrase your own `request_user_input`. Use the exact `next.interaction` / `interaction` returned by SpecRail. A visual gate is deliberately two-step. If `interaction.tool === "host_actions"`, there is **no user decision yet**: render the complete `interaction.presentation.markdown` — the complete authoritative Review Bundle — without summarizing, then execute only the returned `interaction.actions` in order. Every `present-image` action must surface that canonical attachment **inside the conversation**; opening a file picker, printing a path, or naming Before/Proposal/After does not count. Only after the host action actually succeeds record that exact action with `specrail presentation record` using the stable session, current `presentationDigest`, exact `action.id`, and outcome `presented`. Never pre-acknowledge or invent success. If a required image cannot be presented, record `failed` or `unavailable` with a concrete detail, stop with `PRESENTATION_SURFACE_UNAVAILABLE`, and do not ask for approval. After all returned host actions are resolved, call `next` again in the same session. Only when SpecRail returns `interaction.tool === "request_user_input"` may you forward its exact `questions`. A stale digest, different session, edited runtime acknowledgment, or changed evidence must force presentation again. `$visualize` may improve the review, but it never replaces this acknowledged direct fallback.
8. Treat Review Cockpit generation and host presentation as different states. `specrail review cockpit` only prepares a durable local HTML artifact; never claim it is open, rendered, attached, or visible unless the host returns a concrete successful presentation/open result. For a returned `open-url` action, first try to open the exact `openUrl`. Record `opened` only after a successful host open. If automatic opening is unavailable, expose that exact URL as a clickable **Abrir Review Cockpit** browser action/link and record `offered`; never print only its filesystem path. If neither open nor clickable-link presentation is possible, record `unavailable` with a concrete reason; Cockpit is non-blocking only when the required canonical images were successfully presented inline. When `$visualize` is available and the signed gate plan requests an interactive review, attempt it once. `artifactPrepared` and `referencePrepared` are not proof of display; while `hostPresentationVerified=false` / `hostPresentation=unverified`, the mandatory fallback remains every `requiredVisible` image in-conversation plus resolving the `REVIEW-COCKPIT` open action.
9. A phase-boundary `interaction.turnPolicy` is binding. After the native boundary selector returns, persist only that choice with `specrail boundary choose TASK --choice current|pause|fresh --session <session>` according to `choiceMap`, then end the assistant turn. Do not enter the boundary, load implementation context, run CodeGraph expansion, inspect Kanban/memory files, or implement/review in that same turn. The next user turn follows rule 4 and enters the already-chosen boundary without asking again. If the choice is `fresh-chat`, open `next.runtime.transitionNotice.freshChatUrl` when the host supports Codex deep links; it creates a new workspace chat with `Continue TASK-####` prefilled, but the user still sends it.
10. Continue until the next human gate or genuine blocker.
11. Obey `next.autonomy`. On `autonomy-advance`, run the deterministic autonomy advance internally and call `next` again; do not present a human approval. On `headless-stop`, stop and report the unresolved judgment without inventing an answer. Otherwise continue until the next human gate or genuine blocker.

## SpecRail Fast
`SpecRail Fast:` is explicit authorization for a shorter governed workflow, never a blind bypass. The task stores `workflow_mode: fast`. While its sealed control profile remains `micro` or `light`, defer CodeGraph/project-wide Product Owner bootstrap, use compact specification work, and skip separate pre-implementation approval, phase boundary/worktree, UX/ImageGen, independent Technical Reviewer, QA-agent, Target Audience/Final Customer, and durable-learning gates. `micro` still requires exact blast radius, stable ACs, real served After + layout evidence, Scope Guard, Acceptance Coverage, and final user approval; `light` additionally requires focused real Before when applicable. If refinement classifies the task `standard` or `rigorous`, Fast becomes inactive automatically and the normal 0.10 workflow—including Product Intelligence, CodeGraph and approval/review gates—resumes. Do not fight that escalation.

## Environment repair and workflow experiments
- For setup failures, use `doctor --fix` as a plan first. Present its native decision; apply only the listed safe/reversible fixes after approval. Never silently install or change external Node, Git, CodeGraph, MCP, or host plugins.
- Replay is an experiment, not normal task execution. Create it only from an approved unchanged specification with sealed QA Mission. Each harness variant gets a fresh isolated worktree/context, must not inspect another variant, preserves identical verification, records real evidence, and is compared only after equal acceptance + QA checks. Record exact variant-total input/cached-input/output token usage only when the host exposes an aggregate covering the whole Harness run; never estimate missing usage and never compare token cost across different/unknown models. Never collapse replay trade-offs into an invented quality score.
- Historical Harness recommendations are advisory. Use `harness recommend` only after enough comparable replay data exists, explain its evidence/trade-offs, and never change `execution_profile` silently.
## Visualize
Visualize is an optional Codex skill, not a host tool name. Before a gate that has a visualization plan, inspect the current Codex skill catalog. If the exact skill `visualize` is present, internally record it for the stable session with `specrail capability visualize record --availability available --skill visualize --session <session>`; if it is absent, record `unavailable` with a concrete reason. Then regenerate/read the gate interaction so its signed plan reflects that capability state. Never expose these internal commands to the user.

When the signed visualization plan materially improves review, invoke the exact skill explicitly as `$visualize` in the same turn: Review Cockpit, option comparison, workflow timeline, Visual Comparator v2 for before/proposal/after, request/response explorer, architecture layer explorer, migration explorer, or final review tabs. Do not ask the user to type `/visualize`; that slash command is only a composer shortcut. Do not inspect `~/.codex/plugins/cache`, depend on a plugin version, or call Visualize's internal `render.py` directly. A turn that will invoke `$visualize` must follow Visualize's silence contract: do not send progress/commentary before the final review surface unless genuinely blocked.

Pass `$visualize` the signed plan's title, purpose, interactive experience, canonical payload, and source attachments. When `visualization.experience.pattern` is `visual-comparator-v2`, render one interactive comparator root marked `data-specrail-comparator="v2"` with all three modes (`side-by-side`, `slider`, `overlay`), viewport filtering, route/target filtering, capture-scope filtering, visible route/target/capture context, and explicit missing-role errors. Group comparisons by the exact route + target + viewport + capture scope and never slider/overlay images from different contexts. Put `data-specrail-comparator-source="v2"`, `data-specrail-review-role="before|proposal|after|supporting"`, `data-specrail-route`, `data-specrail-target`, `data-specrail-viewport`, and `data-specrail-capture-scope` on each canonical `<img>` (when those values exist) as well as its evidence ID. A static gallery or cross-context pair does not satisfy this plan. The fragment must also contain explicit range controls marked `data-specrail-control="split"` and `data-specrail-control="opacity"`, plus a `<script data-specrail-comparator-runtime="v2">` runtime that binds the mode/filter controls and implements slider clipping and overlay opacity. Every source ID listed in `visualization.requiredSourceIds` is mandatory: the generated fragment must put `data-specrail-evidence-id="<ID>"` directly on the `<img>` that embeds the corresponding canonical image as a `data:image/...;base64,...` source. A marker on a wrapper, caption, hidden node, or text-only block is not evidence of display. If even one required source is omitted, hidden, broken, represented only by text, or uses an unresolved local path, record `failed`/`fallback`; never `rendered`. Let the Visualize skill create its task-owned HTML fragment outside the checked-out repository and emit the native `visualize` content reference. The visualization content reference must be included in the visible review before `request_user_input`; generating either SpecRail's local Cockpit HTML or Visualize's fragment without emitting the native content reference is not proof that the user saw it. Record `rendered` only as evidence that the Visualize HTML artifact and its exact native reference were prepared and validated; it is not a claim that the host displayed them. The run record must therefore remain `hostPresentation=unverified`, `hostPresentationVerified=false`, and `fallbackRequired=true` until SpecRail gains a trusted host-presentation signal. Record provider `$visualize`, exact plan/source digests, the exact native `visualize` content reference returned in that turn, the same absolute fragment path referenced by it, a non-trivial result summary, and the required quality evaluation. If Visualize cannot produce that reference, record `failed` or `fallback`, never `rendered`. Invoke at most once per gate. Markdown, the complete Review Bundle, and canonical evidence remain authoritative and must still be shown; Visualize is the preferred native interactive Cockpit surface when available but remains non-blocking. For every local image source, read the canonical bytes and embed them in the generated Visualize fragment as a `data:image/...;base64,...` URL inside its marked evidence block. Never use `file://`, an absolute filesystem path, or a repository-relative path as `<img src>`; those produce broken evidence in Codex. Keep the Visualize fragment under its 1 MB contract: embed the canonical evidence bytes exactly and add `data-specrail-source-sha256="<canonical sha256>"` to the same `<img>`. SpecRail verifies the embedded bytes against the canonical digest. If the exact images would exceed Visualize's fragment limit, use the Cockpit/attachments fallback instead of silently downscaling or substituting the evidence.

## Phase handoffs and Codex model selector
SpecRail never chooses, stores, recommends, or validates a model. The active model and reasoning setting always come from the Codex selector. SpecRail only controls **phase context** and deterministic handoffs.
- `thinker`: keep repository context bounded (`fast` normally, `standard` only for large/high-risk/rigorous planning). Do not preload implementation files just because they might be useful later.
- `implementer`: the planning → Builder transition is a **session-bound phase-entry boundary plus a required host-turn stop, not a mandatory new chat**. SpecRail can mechanically verify phase entry and session ownership, but Codex does not expose a trusted turn ID. When `next.userInputRequired === true` at `action=phase-boundary`, MUST present `next.interaction.questions` exactly through native input; do not summarize or replace them. The three choices are continuation with the current selector, pause to change model/reasoning in the real Codex selector, or a fresh chat. None starts implementation in the approval turn. After the user chooses, end the turn without entering the boundary or coding. Follow `runtime.boundary.recommendation`: `same-chat-ok` means the next turn may safely continue in the current chat; `fresh-chat-recommended` means recommend a new Codex chat for real token/context isolation. The user may keep or change the model in the normal Codex selector either way.
- On the next user turn, or in the fresh chat, enter the boundary before phase work with `specrail boundary enter TASK --session <stable-session-id>`. The command infers `same-chat` when the stable session is unchanged and `fresh-chat` when a new session enters. Then call `specrail next` again. Do not implement until `runtime.boundary.status` is `entered` and `stopBeforePhaseWork` is false.
- Treat `runtime.handoffPath` as the **compiled implementation capsule**. Read it completely before editing. Previous conversational reasoning is non-authoritative. Do not automatically reread the full canonical task: only open the specific canonical section when the capsule marks truncation, reports a conflict, or a concrete missing detail is needed. The capsule is deliberately executable by a less-capable implementation model: authoritative decisions, execution order, ACs, Scope Guard, QA Mission, UI proposal/evidence, context seeds, Definition of Done, and stop/escalation conditions are explicit.
- `reviewer`: use the same strong/flexible boundary at the first Technical Review transition. Enter it before review work. A fresh chat is recommended when `runtime.boundary.recommendation` says so; same-chat review remains valid after boundary entry for small low-risk changes. QA and Final Customer continue the reviewer context unless SpecRail routes elsewhere.

After any command or native approval that changes the phase, call `specrail next TASK --session <stable-session-id>` before doing work for the new phase. If the command response itself has `userInputRequired=true`, its top-level `interaction` is authoritative: present it exactly, do not continue, do not implement, and end after the user's boundary choice. Never silently cross planning → implementation or implementation → independent review in one assistant turn. Never copy the full prior chat into a handoff. A same-chat continuation provides a logical authority reset but does **not** save the previous conversation tokens. A fresh chat provides both the logical reset and raw context reduction.
## Frontend runtime previews
For frontend/UI work, make `UI Target` deterministic before generating evidence: declare each context in `Route/Ruta → Target/Objetivo → exact pixel Viewport(s) → Capture/Captura` order. Treat route and target identity as exact/case-sensitive. Every declared route + target + viewport + capture scope requires its own canonical Before + Proposal, and its own After when implementation evidence is required. Do not present historical evidence from a context no longer declared by the current `UI Target` as an active proposal/comparison source.

For frontend before/after evidence and any user-facing website preview, use the real application served over `http://` or `https://` from the correct project/worktree. Never present or open a raw `index.html`, `file://...`, or filesystem path as the website preview. Start the runbook/dev/preview server, wait until the target URL responds and the requested DOM is rendered, keep that server alive through the human review gate, and register the exact served URL with evidence (`--url`). If `presentation.previewUrl` is returned, open that exact URL for the user; health-check/restart it first if needed. A white/blank file preview is not valid evidence.
A shell sandbox failure to reach `localhost` is not evidence that the Codex host browser cannot reach the same served application. For frontend automated visual QA, first ensure the dev/preview server is alive. If the current host exposes Browser, invoke that surface against the exact `http://`/`https://` runtime URL and record `surfaceClass=host-browser`, the concrete surface, `attemptRef`, and `targetUrl`; a shell probe can never substitute for that attempt. If the current host exposes no Browser capability, record `hostBrowser=unavailable`, `surfaceClass=host-without-browser`, `attempted=false`, no `attemptRef`, and the concrete host limitation. Only those two cases may produce `AUTOMATED_VISUAL_QA_UNAVAILABLE`; shell failure alone may not. Keep human inspection separate from automation: a manual check may be recorded as `verification.type=human`, while attempted automated results require `automated|mixed` and required automated visual QA remains blocking when `unavailable` or `failed`.
## Human decisions — use `request_user_input` for ambiguity, scope, architecture, data, security, privacy, migrations, important UX, eval activation, repair-limit recovery, and any approval/delivery gate that the active autonomy policy returns as human-owned. Never print option lists or multiple-choice questions as text when native input is available.

## Workflow invariants
- Product Specifier refines until no material ambiguity remains, writes the immutable executable QA Mission, selects risk-based quality and operational evidence, and creates vertical slices for large features.
- The deterministic specification linter must pass. Approval hashes the governed specification; any governed change invalidates approval.
- Generate the read-only Review Cockpit plus authoritative `review-bundle`; show both before each approval.
- Failures and material user rejections are classified. Repeated failure patterns become eval candidates, activated only after user approval. A bounded Final Approval refinement is normal `REV-*` iteration, not a failure and not a repair attempt. Load `activeEvals` returned by deterministic routing and run them as regression checks before completing the matching phase.
- Repair loops are finite. After the profile limit, stop and consult the user.
- Constitution principles require user approval and a deterministic enforcement command.
- Frontend before evidence must focus the exact task target. Proposals use the official installed Taste Skill workflow and Image Gen; final evidence uses the real app and browser/DevTools.
- High-risk or material UI work requires an independent Technical Reviewer with fresh context.
- Property testing, mutation testing, logs, traces, and metrics run only when selected by risk.
- Large features execute as small demonstrable vertical slices, not horizontal frontend/backend/database-only layers.
- Do not spawn subagents for trivial work. Outside a deterministic concurrency plan, use at most three read-only subagents for useful parallel analysis. When `next.action` is `prepare-concurrency-wave`, load `ai-flow-multi-agent`, prepare exactly the returned lanes, and use host subagents only for those reservations. Each lane keeps the session ID returned for that reservation; a later re-dispatch gets a new identity; task-local lanes may analyze/refine in parallel, while writing lanes require approved non-overlapping Scope Guard boundaries and separate worktrees. If the host cannot spawn subagents, execute the same scheduler lanes sequentially; never run conflicting write lanes together.
- Code or migration work uses a task worktree. Done requires final approval and explicit delivery/merge; use `delivery merge` or externally confirmed delivery.
- Store structured traces and metrics locally only; no external telemetry.
For frontend work, the primary screenshot must focus the exact task target; page-top and full-page captures are context only.

## Acceptance, scope, and change requests
Before specification approval, require stable `AC-*` criteria and a CodeGraph-informed Blast Radius for implementation tasks. Final approval requires 100% canonical Acceptance Coverage and a clean Scope Guard. Evidence must declare the criteria it proves.
After approval, governed scope is immutable except through a Specification Amendment. A bounded `REV-*` may refine only the already-approved implementation/result inside its guarded boundary; it does not rewrite the base specification. Present every proposed amendment with reason, added acceptance criteria, blast-radius changes, and impact using the native `request_user_input` gate. Never self-approve an amendment or silently edit the approved base specification. Approved amendments extend the effective specification hash while preserving the original approval history. For an active `REV-*`, follow the Revision Delta Capsule instead of replaying normal planning. Do **not** design or create a new test before implementing the small requested delta: the desired behavior is still stabilizing. Implement first, gather only the targeted post-implementation evidence SpecRail invalidated, run existing tests afterwards only when cheap/directly relevant, and decide permanent regression coverage after stabilization. If the delta turns out to require a governed product, architecture, migration, security, broad-scope, or breaking-contract change, stop and escalate instead of widening the revision.
