# AI Flow
Do not require the user to mention AI Flow, a skill name, a task ID, or a CLI command, and do not expose internal CLI instructions to the user.

## Entry gate and invariants
For every new delivery work item, choose the process route before any SpecRail task, CodeGraph preflight, gate, evidence state, or learning exists. Unless this is explicit `Continue/Resume/Retoma TASK-####` or a route prefix, use native `request_user_input` with `SpecRail`, `Directo`, `Directo + verificar`, and `Other`/free text. Never select a route for the user.
`Sin SpecRail:` / `No SpecRail:` means bypass SpecRail completely **as workflow state only**: no SpecRail CLI, task, CodeGraph preflight, gate, evidence state, or learning. `Directo + verificar:` / `Direct + Verify:` adds the smallest meaningful final verification. `SpecRail Fast:` selects governed SpecRail and uses `--mode fast`. Never infer total bypass from impatience or wording without an explicit route. Process route is independent of `micro/light/standard/rigorous`, Guided/Autonomous/Headless, and Brain/Worker ownership.
When SpecRail is selected for new work, preserve the **complete active user request** as task `Need` at intake (`specrail intake ... --need <request>` or an equivalent exact task write) before launching any Worker. Never create a title-only task and expect a Worker to reconstruct the request from chat. Immediately after the task exists, show one **Work Capsule** in chat (≤100 words): `TASK-####`, the requested outcomes/constraints, and the next bounded phase. This is an early progress/intent summary, not approval; show it **before** CodeGraph expansion, Worker launch, broad reads, or other heavy work.
For every code-writing route require the official `@dietrichgebert/ponytail` capability in literal `full` mode before mutation. SpecRail installation includes the official Ponytail package and skills, and its Pi package loads the official Ponytail Pi extension when Pi is selected. Missing Ponytail is therefore a broken/incomplete SpecRail installation, not a prerequisite the user should be told to install separately; reload the host or repair/reinstall SpecRail. If Ponytail was explicitly switched away from `full`, ask to restore `full`. Never offer or accept a per-work-item Ponytail bypass. Before a mutation phase completes, run official `ponytail-review` against the diff. User requirements, security/privacy, accessibility, data-loss protection, approved scope, acceptance criteria, and evidence outrank minimalism.
Never fill a material unknown with model confidence. Resolve it from explicit active user input, an approved decision, an authoritative repository contract, one unique established repository pattern, or current deterministic tool evidence; otherwise ask 2–4 concrete choices, at most one recommendation, plus free-text `Other`. Recommendations are never preselected. Never print option lists or multiple-choice questions as text when native input is available.

## Host adapters
- **Codex:** use native `request_user_input`; only after SpecRail is selected use the managed/global `specrail` launcher. The current chat model is the **Brain** and remains selected. Managed SpecRail installs official Ponytail skills alongside SpecRail skills. Worker phases use packaged `specrail-worker`, which starts an isolated `codex exec --model ... --ephemeral` process so worker selection does not depend on inherited subagent model state. `$visualize` is optional and only valid when the exact installed skill is attested.
- **Pi:** use `specrail_entry_gate` for unresolved new-work routing; after SpecRail selection use `specrail_cli`, exact `specrail_host_context`, `specrail_skill`, and `specrail_codegraph`. The current Pi model is the **Brain**. The SpecRail Pi package declares/loads bundled official Ponytail extension/skills. Worker phases use `specrail-worker`, which starts a separate Pi process with explicit `--model`. `/specrail-handoff TASK-####` or `/new` + `Continue TASK-####` remains the fresh-boundary fallback.
- Without an interactive UI, never emulate a process route or human decision in text; stop unless explicit authority already exists.

## Deterministic control
1. Resolve existing work with `ai-flow resolve` by ID, exact title, or unique phrase. Task Markdown is the source of truth. Ambiguity uses the native task selector; never guess or create duplicate intake. Show `TASK-#### — Title`, easy to reference in another chat by ID, title, or descriptive phrase.
2. Let SpecRail own CodeGraph lifecycle. Do not manually run `codegraph init`, `sync`, `status`, or `index` during healthy task routing. Cached contract/health state and the active CodeGraph host transport are authoritative; full reindex is an explicit Doctor repair only. Fast micro/light may defer project-wide CodeGraph until escalation.
3. Read `next` first. If `specrail next` fails, treat it as a runtime blocker; `readiness` and `why-blocked` are diagnostics and never replace routing authority. Load only the returned specialist: on Pi call `specrail_skill`; on managed Codex read `.agents/skills/<recommendedSkill>/SKILL.md`. Do not rely on automatic mid-turn skill reselection and do not keep unrelated skills in context.
3a. `next.intelligence` is authoritative for **Brain/Worker ownership**. `none` means deterministic/human work; `brain` means the current user-selected chat model owns the governed judgment; `worker` means Brain delegates that heavy phase through `specrail-worker` when the packaged launcher is available instead of doing the phase itself. WorkerOrder pins `gpt-5.6-luna` first and may try `gpt-5.6-terra` only when Luna is unavailable as a model. An ordinary Worker failure never promotes automatically to Terra or Brain. Silent Brain-model fallback is forbidden.
3b. A Worker receives an immutable original Request Capsule plus a sealed minimal WorkerOrder—not chat history—with goal, approved authority, bounded context seeds, explicit model candidates, runtime budget, and stop conditions. Worker may reason locally about execution mechanics but cannot decide product intent, architecture, public contracts, security/privacy, migration strategy, governed UX, scope expansion, or consequential user questions. `WORKER_INPUT_INCOMPLETE` means repair only the sealed request/input; `WORKER_ENVIRONMENT_BLOCKED` means repair the child runtime; `WORKER_BUDGET_EXCEEDED` means stop/re-scope the Worker. **None of these authorizes Brain to perform the Worker phase.** Only a validated `ESCALATE_TO_BRAIN` transfers a specific governed decision, never the implementation/specification workload.
3c. Once `specrail-worker` is launched, Brain must not read files, search the repository, edit task sections, materialize the specification, or start a second same-phase Worker while that process is still running. Wait/poll only for that process result. Identical completed/escalated/failed orders are reusable and must not be relaunched unless concrete remediation/new authority changes the order or an explicit `--force` retry is justified.
3d. Do not spawn subagents for trivial work. Brain/Worker delegation is deterministic routed execution, not permission for opportunistic swarms; outside a persisted concurrency plan use at most three read-only subagents for useful parallel analysis.
4. Product Owner judgment is Brain-owned. Product-context bootstrap/spec materialization/Builder/QA/review analysis are Worker-eligible according to `next.intelligence`. Target Audience retains its existing mandatory fresh-session isolation until Worker session independence can be attested; do not weaken that boundary for token savings. Guided asks for acknowledgement; Autonomous/Headless may advance only mechanically safe decisions. A material revise/reject judgment remains human-owned.
5. Bounded post-approval feedback defaults to the same task as `REV-*`; do not regenerate the workflow or create a new task. Implement the small revision first, gather invalidated evidence, then decide permanent regression coverage after behavior stabilizes. Escalate only governed product/architecture/migration/security/breaking-scope changes.
6. Explicit close/finish-anyway or skip requests are governance input only for the deterministic close override or a registry-marked waivable workflow step. They never disable Ponytail, security/data-loss protections, or fabricate passed evidence.
7. Use one stable host session token for every human gate and obey `resolve-task-lease`. Respect the approved specification hash, immutable QA Mission hash, dependencies, repair budget, evidence gates, and `context.policy`; keep context small.

## Approval and presentation
At a human gate, never construct or paraphrase your own `request_user_input`. Use the exact `next.interaction` / `interaction` returned by SpecRail. The approval `request_user_input` question itself begins with the complete `interaction.presentation.markdown` Decision Capsule, so the concise summary is visible in chat **before** the selector even on hosts that do not render presentation metadata. Do not ask for approval in a separate call or before that summary.
When `interaction.tool === "host_actions"`, render the complete `interaction.presentation.markdown` and execute only the exact returned `present-image` actions; there is no user decision yet. Every `present-image` action must surface the canonical attachment inside the conversation. Opening a file picker, printing a path, or naming Before/Proposal/After does not count. Record only actual action outcomes with stable session, current `presentationDigest`, and exact action ID. Required image failure blocks with `PRESENTATION_SURFACE_UNAVAILABLE`. Do not ask for approval until SpecRail returns `interaction.tool === "request_user_input"`.
The complete authoritative Review Bundle remains the `REVIEW-BUNDLE` attachment/Review Details and is available on demand, not dumped into normal chat. Review Cockpit is a legacy manual artifact only: do not generate, open, offer, or use it in the normal approval workflow. Treat artifact generation and host presentation as different states; for a generated review artifact, never claim it is open, rendered, attached, or visible unless the host actually surfaced it. The old mandatory fallback that coupled `requiredVisible` evidence to `REVIEW-COCKPIT` is forbidden; normal fallback contains only exact `present-image` actions. `$visualize` preparation leaves `hostPresentation` unverified; `artifactPrepared` and `referencePrepared` are not proof of display. A stale digest, changed evidence, different session, or tampered acknowledgement forces required visual presentation again.
Normal output is delta-first: at most four short bullets (`%`, implemented, validated, blocker/next) unless the user asks for detail. Blockers, failed ACs, security/data-loss risk, scope violations, and stale/tampered evidence override brevity.

## Phase boundaries and delivery
A phase-boundary native choice is persisted, then the assistant turn ends. On the next turn enter the sealed boundary before implementation/review. Fresh chat is recommended only when runtime says so; same-chat entry is valid after the logical authority reset. Brain/Workers does **not** require changing the main-chat model at Worker boundaries: Brain stays selected while the isolated cheaper Worker process runs. Read the compiled handoff before work and do not copy full prior chat.
Done requires final approval and explicit delivery/merge. Use `delivery merge` or externally confirmed delivery; never equate implementation with delivery.

## SpecRail Fast
`SpecRail Fast:` is a shorter governed workflow, not a blind bypass. Micro/light defers project-wide Product Intelligence/CodeGraph and unnecessary agents, while preserving exact blast radius, stable ACs, real proof, Scope Guard, Acceptance Coverage, Ponytail full/review, and final approval. If deterministic classification reaches standard/rigorous, the normal 0.10 workflow resumes.

## Frontend and Visualize
Frontend work declares exact `Route → Target → pixel Viewport → Capture`. The primary screenshot must focus the exact task target; page-top/full-page captures are supplementary. Proposals use the installed Taste Skill workflow and Image Gen where applicable; final evidence uses the real app and browser/DevTools.
Serve previews over `http://` or `https://`; never use raw `index.html` or filesystem paths as website previews. Never use `file://` previews. If `presentation.previewUrl` exists, use it. Shell localhost failure is not Browser failure. Canonical generated image evidence uses `data:image` / data URI bytes and puts `data-specrail-evidence-id` directly on the `<img>`; unresolved local paths produce broken evidence and are invalid.
Discover the exact installed `visualize` skill from the Codex skill catalog. Do not ask the user to type `/visualize` and do not call `render.py` manually. Invoke `$visualize` only from a signed plan when it materially improves review. A valid Visual Comparator v2 keeps exact route/target/viewport/capture context, canonical evidence IDs and hashes, and interactive side-by-side/slider/overlay controls. Emit the native `visualize` content reference; generated HTML alone is not presentation. Record `rendered` only for validated artifact/reference preparation, while hostPresentation remains unverified and fallback remains required.

## Workflow invariants
- Product Specifier removes material ambiguity, writes executable QA Mission, stable `AC-*`, and risk-selected evidence. The deterministic specification linter must pass; approval hashes the governed specification.
- Final approval requires canonical Acceptance Coverage and clean Scope Guard. Governed scope changes use an Amendment; bounded `REV-*` does not rewrite the approved base specification.
- Brain/Worker delegation is distinct from feature-level Multi-Agent Concurrency. Worker processes never recursively spawn Workers. Existing concurrency still governs parallel task lanes, leases and non-overlapping write scopes.
- Repair loops are finite. Required tests/evals/evidence stay risk-selected and deterministic. Store traces/metrics locally only; no external telemetry.
- Environment repair uses `doctor --fix` as a plan and never silently installs Node, Git, CodeGraph, MCP, or arbitrary host plugins. Ponytail is a declared SpecRail runtime dependency handled by SpecRail installation; repair missing bundled Ponytail by repairing/reinstalling SpecRail rather than installing an unrelated substitute.
